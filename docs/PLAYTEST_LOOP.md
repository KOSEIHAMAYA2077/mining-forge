# 試作 → プレイ → 設計修正 → 再試作の進め方

更新日：2026-09-07。P0a-02の見た目への感想とシステム再現の依頼を受け、P0a-03を実装中。呼称は活性度でよい。試遊版の現在地と検証結果は [CURRENT](handoff/CURRENT.md)。最新のユーザー指示で、この設計相談でもコードの実装・ビルドへ進んだ。

## 初回に実装担当へ渡すもの

このWindowsではCodexのプロジェクトの作業フォルダに、次のリポジトリルートを指定する。

```text
C:\Users\kouha\Documents\ChatGPT\採掘系のゲーム作成？
```

初回はこのフォルダで作業するローカル環境を使う案。Unityプロジェクトの作成先はその中の `game/`。最初から `game/` だけを作業フォルダに指定せず、設計とAGENTSも含むリポジトリ全体を渡す。別端末では [GitHub](https://github.com/KOSEIHAMAYA2077/mining-forge) をcloneしたルートを使う。

ローカル環境は現在のプロジェクトディレクトリで作業する。Worktreeを使う場合は別の作業コピーになるため、その担当に実際の試作と起動ファイルの場所を報告させる。[公式の環境説明](https://learn.chatgpt.com/docs/environments/modes)

次の文章を初回依頼に使える。

> このリポジトリのAGENTS.mdとdocs/START_HERE.mdを読み、Issue #1のP0aを実装してください。docs/PROTOTYPE_0.mdを仕様として、まず結晶1個を採るところまで作り、私が遊べる状態で一区切りにしてください。詳細な品質要件はdocs/handoff/IMPLEMENTATION_PROMPT.mdを参照し、今回の範囲はP0aまでを優先してください。Kenney素材を活用し、見た目・打撃エフェクト・音を含めてください。必要な動作確認と修正を行い、起動場所・操作方法・試作の版・GitHubのPR・確認済みと未検証・試してほしい点を報告してください。docs/PLAYTEST_LOOP.mdに従って記録を残してください。

最初の一周を短くするためP0aでユーザーのプレイを挟む。P0全体にはP0bの3系統と工房の循環も必要であり、削除したわけではない。

## 実装担当がプレイ前に残すもの

起動できるビルド、またはUnity上での具体的な再生手順を用意する。実行できなかったものは「プレイ可能」と扱わない。

毎回、次の情報を最終報告と `docs/handoff/CURRENT.md` に残す。

- 試作名：例 `P0a-01`。異なる内容を同じ名前で配らない。
- ソースのコミットIDと作業ブランチ、PRのURL。
- 起動ファイルの絶対パス、またはUnityで開くフォルダとシーン・操作手順。
- 実際に確認した動作と既知の問題。
- 今回ユーザーに試してほしい点を1〜3個。

ビルドはコミット済みのゲーム内容から作り、どのソースか追えるようにする。ビルド後の報告だけを別コミットにする場合は、ゲームを作ったコミットIDと報告のコミットIDを区別する。ローカルの実行ファイルはGitHubへのコードpushだけでは他端末へ届かない。別端末で遊ぶ場合は、ビルド一式の渡し方か再ビルド手順を別に示す。

## ユーザーがこの設計相談へ戻すもの

**実装担当の最終報告を貼り、感想を添えるだけでよい。** PRや試作名を報告へ入れるのは実装担当の仕事。ユーザーがコミットIDを手で調べる必要はない。

短いプレイなら5〜10分を目安に、次を自由文で伝える。全項目必須ではない。

- 気持ちよかったところ。
- つまらない・分からない・面倒だったところ。
- そう感じた場面、選んだ技、結果。
- どうなってほしいか。まだ分からなくてもよい。

例：「強打の音は良い。でも3回とも通常打撃ばかり使った。微調整を使う理由が分からない。」数字の変更案まで考える必要はない。スクリーンショットや短い動画があると、表示や操作の問題を特定しやすい。

記録用のひな形は [PLAYTEST](templates/PLAYTEST.md)。会話に貼られた内容は、設計担当が `docs/playtests/YYYY-MM-DD-試作名.md` に整理して保存する。まだプレイしていない評価を埋めない。

## 設計担当が行うこと

1. PRまたは指定ブランチの該当コミットを読み、遊んだ版と現在のコードを区別する。非公開リポジトリへアクセスできない環境では、ユーザーに実装報告と必要な資料を渡してもらう。
2. 感想を「観察したこと」「原因の仮説」「変更案」に分ける。実際にプレイを見ていない場合、原因を断定しない。
3. バグ、表示・操作、バランス、企画変更を区別して優先順位をつける。一周で直す主な体験上の問題は1〜3個程度に絞る。
4. 次に試す変更を [CHANGE_REQUEST](templates/CHANGE_REQUEST.md) の形式で `docs/handoff/changes/CR-001.md` などへ保存する。検討中なら「検討中」、次に実装する内容なら「実装対象」と明記する。
5. 決めた変更はPROTOTYPE_0へ反映する。中心方針が変わるならMASTERとDECISIONSも更新する。Issue、STATUS、CURRENT、セッションメモを更新し、コミットしてpushする。
6. ユーザーへ「変更仕様の場所・参照コミット・対象Issue・実装担当へ貼る短い依頼」を返す。

この設計相談ではゲームコードを直接直さず、試したい変更を具体化して実装担当へ渡すのを通常の役割分担とする。コード修正も明示的に依頼された場合は、その範囲で対応する。

## 修正を実装担当へ戻す

同じ実装タスクへ、次の形で依頼する。CR番号と参照コミットは設計担当が実際の値を埋めて返す。

> プレイ結果を基に変更仕様をGitHubへ保存しました。指定されたコミットの変更仕様と更新済みの試作仕様を読み、今回の実装対象を修正してください。ゲームの作業ブランチへ設計更新を取り込み、確認・再ビルド・作業記録・pushまで行ってください。新しい試作名、起動場所、変更点、確認結果、比較してほしい点を報告してください。

変更仕様に書いていない新機能を感想から推測して追加しない。明確な不具合の修正は実装担当へ直接頼んでもよい。その場合も修正内容と確認結果を記録して、この相談から追える状態にする。

## ブランチと共有フォルダで混乱しないために

mainは統合済みの正本。未統合の試作品は作業ブランチとPRにあるため、設計担当はmainだけを見て「まだ実装されていない」と判断しない。

同じフォルダで設計担当と実装担当が同時に書き換えない。実装が一区切りになり、変更をコミット・pushしてから設計の見直しへ移る。別ブランチの調査はGitHubや独立した作業コピーで行い、未保存のゲームを含むフォルダを勝手に切り替えない。

設計修正をmainへ保存した場合、実装担当はその更新を自分の作業ブランチに取り込んでから修正する。単に取得しただけで取り込み済みと扱わない。内容を確認して競合を解消し、force pushで履歴を消さない。機能ブランチをmainへ統合する操作は、ユーザーの指示に従う。

## 二周目以降

修正前後で同じ対象・条件を使い、「通常打撃ばかりだったのが、仕上げで微調整を選ぶようになったか」のように判断の変化を見る。初回の感想を過剰に一般化しない。良くなった・変わらない・悪くなったを記録し、次の一件を選ぶ。

採取の操作感が成立したらP0bへ進み、結晶・遺物・魔力を持ち帰る目的の違いを試す。撤退条件の追加はその後のP1で扱う。
